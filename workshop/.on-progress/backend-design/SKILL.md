# Backend design

A pool of rules. It owns no process: consult the sections the current decision or code touches, and let the calling workflow (grilling, wayfinder, implementation, review) own the steps and the deliverable.

Project ADRs and the glossary win over these defaults. A deliberate deviation is a decision worth recording as an ADR.

Vendors, products and libraries already in the project are the given. Adding or replacing one is the user's decision: present the candidates as options, each with its trade-off, and recommend by requirement.

Beside this file:

- **Grilling or design review:** read [CHOICES.md](CHOICES.md) before the first question. Its defaults are the recommended answers for architecture style, API style, sessions, authorization model and caching; a recommendation drawn from it names its entry (`CHOICES: API style`).
- **At session start, once the stack is known:** read [SERVERLESS.md](SERVERLESS.md) if the code runs on serverless or edge functions; invoke the `database-design` skill if the system of record is a relational database.

## Stance

- **Assume the network fails.** Every remote call can time out, run twice, arrive out of order, or half-succeed. Design and code for that case first.
- **Simplest thing that meets a stated requirement.** Every added component (service, queue, cache, replica) names the requirement that pays for it, and leaves a clear next scale step.
- **Name the trade-off.** Every significant decision states the alternative rejected and why.
- **Numbers over adjectives.** Targets are measurable: p95/p99 latency, availability, peak req/s, RPO/RTO, cost per month.

## A backend design is ready when

Each item has a recorded answer, an explicit assumption, or "not applicable", in the spec or an ADR:

- **Dependencies:** a table of every external dependency with its timeout, retry policy, fallback, and what the user sees when it is down (see Failure handling).
- **Idempotency:** each state-changing operation's behaviour under repetition; for keyed operations, the replay, 422 and 409 behaviour and the key retention window (see Idempotency).
- **Rate limits:** per user, tenant or key, answered with 429 + `Retry-After` (see Failure handling).
- **Placement:** where compute runs relative to its data (see SERVERLESS.md when it applies).
- **SLOs:** what is measured, the target, and the error budget (see Observability).
- **Rollout:** how a change reaches users and what triggers rollback (see Deployment and evolution).
- **Out of scope:** written down; unstated scope is where designs go wrong.

## Code shape

- **HTTP at the edges.** Transport (routing, parsing, input validation, identity, status codes) → application/domain (use cases, business rules, authorization decisions; framework-free) → infrastructure (storage, queues, external APIs behind interfaces).
- Validate input once, at the boundary: type, size, range, format.
- Bound every request: body size, page size, timeouts, and the cost of expensive calls (AI, SMS, email).
- Independent remote calls run in parallel; sequential round trips add up.
- Handlers that return lists follow the list-query rules under Access patterns in the `database-design` skill: no N+1, no row explosion, bounded columns and child collections.

## Failure handling

- Every remote call has a timeout set below the caller's own deadline; propagate the deadline downstream.
- Retry only idempotent or keyed operations: exponential backoff with jitter, capped attempts, a retry budget against retry storms.
- For every external dependency, record: timeout, retry policy, fallback, and what the user sees when it is down.
- Keep core journeys working when non-core dependencies fail: per dependency choose hide, fallback, stale cache, or read-only.
- Under overload, rate limit per user/tenant/key (429 + `Retry-After`) and shed cheap-to-reject work first.
- Circuit breaker, bulkhead and rate-limit state lives where every instance shares it; a per-process counter protects only its own process.

## Idempotency

Every state-changing operation has a defined behaviour under repetition.

- Naturally idempotent: full-resource PUT, DELETE, "set status to X", upsert by natural key.
- Non-idempotent creates (payment, order, email) take an **idempotency key**, generated by the client per logical operation. The server stores key → (request fingerprint, status, response):
  - same key, same payload → return the stored response;
  - same key, different payload → 422;
  - same key while the first is in progress → 409;
  - scope keys per tenant/client; expire after a retention window (e.g. 24 h).
- A uniqueness constraint in the store is the final guard against duplicates.
- Queue, event and cron handlers are at-least-once: dedup via an **inbox** (processed message ids) written atomically with the side effect.
- External side effects (charge, email) carry the provider's idempotency key and run after the local commit, via the outbox.

## Consistency

- All state in one transactional store → one transaction. Modules stay separate in code and share the transaction.
- A write plus a message or external call goes through a **transactional outbox**: business change and outbox record committed together; a relay publishes afterwards, in order, at-least-once. Without an outbox, a dual write needs a reconciliation job.
- A business transaction across services or external systems is a **saga**: local steps, each with a compensating action (refund, release reservation). Default to orchestration; see CHOICES.md for when choreography fits.
- Across services and brokers, consistency comes from local transactions plus outbox/saga; distributed two-phase commit stays out.
- Every read path states its contract: strong, read-your-writes, or eventual within N seconds.
- With replicas or caches, the acting user still sees their own writes: carry a version token, or route their reads to the primary for a short window.
- Concurrent updates use a version field or ETag with a conditional update (`If-Match` → 412 on mismatch).

## Async messaging

- A queue consumer is: idempotent; retried with backoff; backed by a dead-letter queue with an alert and a replay procedure; fed references, not blobs; explicit about ordering (per-key via message groups/partitions when needed); monitored on depth and age of oldest message.
- **Events** state past-tense facts with no expected handler (`OrderPlaced`). **Commands** ask one specific component to act (`SendInvoice`). Name each by what it is.
- Event schemas evolve additively and carry a version.

## API contract

- Resources model the domain, not storage. State transitions with business meaning are explicit actions (`POST /orders/{id}/cancel`).
- HTTP semantics hold: GET is safe; PUT and DELETE are idempotent; POST becomes idempotent via a key.
- Pagination is cursor-based with a bounded page size and a stable sort (tie-break on a unique id). Total counts are opt-in (a query flag or a separate endpoint), since counting large collections is expensive.
- A mutation's response carries the updated resource, so clients update their cache without a refetch.
- Filtering and sorting accept whitelisted fields only.
- Errors use one format (RFC 9457 problem details): stable machine code, human message, field-level details, correlation id. 4xx means the caller can fix it; 5xx means we must.
- Long-running operations: 202 + an operation resource to poll, or a completion event/webhook.
- Data conventions: timestamps ISO 8601 UTC; money as integer minor units or decimal string plus currency; opaque string ids; one casing throughout.
- Evolution: additive changes within a version; tolerant readers; deprecation with a timeline; breaking changes get a new version. Old clients (mobile apps, open tabs) live a long time.
- One contract definition drives validation, docs and client types.
- **Outbound webhooks:** signed; event id + timestamp for dedup and replay protection; retried with backoff; versioned, since ordering isn't guaranteed; thin payload with a fetch-latest option.
- **Inbound webhooks:** verify the signature, dedup by event id, acknowledge fast and process async.

## Authentication and authorization

- Identity comes from a managed provider or a maintained auth library; hand-written credential, OTP or session code is the deviation.
- Browsers get httpOnly, Secure, SameSite cookies set by the backend/BFF, with CSRF protection on every state-changing request (SameSite narrows CSRF; a token or origin check closes it). Service-to-service uses workload identity or scoped API keys.
- Transport establishes identity; the domain layer authorizes every use case, deny by default.
- Every access passes three checks: **object-level** (may this caller touch this id — the top API vulnerability class), **function-level** (admin operations), **property-level** (which fields are readable/writable; explicit field allowlists on writes).
- Review designs against the current OWASP API Security Top 10.

## Multi-tenancy

The tenancy model itself (shared tables, schema or database per tenant) is a data-layer choice owned by `database-design`.

- Tenant context comes from the authenticated identity, never from client input alone, and reaches every data access by construction (repositories require a tenant id, or the store enforces it).
- Per-tenant rate limits and quotas guard against noisy neighbours.
- Tenant id appears in logs, metrics and cache keys.
- Tenant data export and deletion have a defined path.

## Caching

- Cache after measuring a need; well-indexed storage is often enough.
- Every entry has a TTL and an invalidation trigger.
- The system stays correct with an empty or flushed cache.
- Stampede protection: request coalescing, early refresh, jittered TTLs.
- Keys for user- or tenant-scoped data include the user/tenant.
- HTTP caching (`Cache-Control`, ETag + conditional requests) comes first for public and revalidatable data.
- In-process caches are per instance: they hold only immutable or truly global data; shared data goes to a shared cache.

## Observability

- Structured logs carry correlation id, tenant, user and route; secrets and unneeded PII stay out.
- Metrics: RED per endpoint (rate, errors, duration), USE per resource (utilization, saturation, errors).
- Traces span API → queue → worker → storage; trace context travels inside messages.
- SLOs measure what users feel (core endpoint availability, p95 latency, queue processing delay), with an error budget. Alert on burn rate and user-facing symptoms, plus data-at-risk signals (DLQ non-empty, outbox lag).
- Business monitors (orders per minute, failed payments) catch what technical metrics miss.
- Security-relevant and admin actions go to an append-only audit log: who, what, when, from where.

## Security and data protection

- Secrets live in a secrets manager or platform bindings and are rotated; code and logs never hold them.
- Least privilege per identity: the runtime identity cannot change schema or infrastructure; migrations run under a separate identity; API keys are scoped.
- Encrypt in transit and at rest; classify data (public / internal / confidential / regulated); store and log the minimum.
- Third-party API responses are untrusted input.
- Fetching user-supplied URLs goes through an SSRF guard: allowlist, private address ranges blocked, redirects re-checked.
- Uploads go direct to object storage via short-lived signed URLs, are validated/scanned async, and are served from a separate origin with safe content types.

## Deployment and evolution

- Old and new code run side by side during every deploy: each change stays backward compatible through the rollout.
- Schema changes (storage, events, contracts) follow expand → migrate → contract, decoupled from code deploys.
- Ship behind feature flags with canary or percentage rollouts and automated rollback on SLO regression.
- Preview environments get isolated data.
- Identify the cost driver early (often storage, egress or log volume rather than compute) and shape caching and batching around it.
