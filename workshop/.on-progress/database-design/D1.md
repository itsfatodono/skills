# Cloudflare D1

How the rules in [SKILL.md](SKILL.md) land on Cloudflare D1, which is SQLite behind a Worker binding. Numbers and feature status are as of November 2026; verify against developers.cloudflare.com before relying on one.

## Transactions and concurrency

- There are no interactive transactions: the binding has no `BEGIN` … `COMMIT` that spans application code. The unit of atomicity is one statement or one `batch()`.
- `batch()` is a transaction: statements run in order, and one failure rolls back them all. Later statements cannot branch on earlier results in application code, so a dependency is written in SQL (subquery, `INSERT … SELECT`).
- Each database runs one query at a time, so a single statement or batch never interleaves with another writer. Row locks, `FOR UPDATE` and skip-locked claiming do not exist.
- Concurrency rules live in a constraint or a single conditional statement, then the affected row count (`meta.changes`) decides the outcome:
  - state transition: `UPDATE … SET status = 'closed' WHERE id = ? AND status = 'open'`;
  - limit: `INSERT … SELECT … WHERE (SELECT count(*) FROM …) < N`;
  - job claim: `UPDATE … WHERE id = (SELECT id … LIMIT 1) RETURNING …`.
- Zero rows changed means the rule rejected the write. Read-then-write across two calls races.

## Scale

- One database is single-threaded: throughput ≈ 1 ÷ average query duration (1 ms → ~1,000 queries/s, 100 ms → ~10). Excess requests queue, then fail as overloaded.
- Database size is capped (see Limits) and the cap cannot be raised: D1 scales out across many small databases, per tenant or per entity. This is the signal to deviate from `CHOICES: Tenancy model` toward database per tenant.
- Fewer, indexed queries are the first lever: a `batch()` counts as one query and one round trip.
- Bulk updates, deletes and backfills run in chunks of about 1,000 rows.

## Types and ids

- Columns have type affinity, not enforced types. Tables are created `STRICT` so a wrong-typed value is rejected.
- Time: ISO-8601 UTC text (`2026-11-27T09:30:00.000Z`, fixed width so it sorts) or integer epoch. One choice per schema.
- Money: integer minor units plus currency. Integers come back as JavaScript numbers, exact only up to `Number.MAX_SAFE_INTEGER`; BigInt is not supported by the API.
- Booleans: `INTEGER` with `CHECK (col IN (0, 1))`; they read back as `0` / `1`.
- Closed value sets: `TEXT` with a check constraint.
- UUIDv7: generated in the application, stored as `TEXT`.
- Binding `undefined` fails with `D1_TYPE_ERROR`; absent values are bound as `null`.

## Constraints

- Foreign keys are always enforced and cannot be switched off. `PRAGMA defer_foreign_keys = on` postpones the check to the end of the current transaction; `PRAGMA foreign_key_check` lists violations.
- Foreign keys are **not** indexed automatically.
- Check constraints carry single-row rules. Conditional uniqueness is a partial unique index (`… WHERE status = 'active'`).
- There are no exclusion constraints. No-overlap rules are a conditional statement (`INSERT … SELECT … WHERE NOT EXISTS (overlapping row)`) or a `BEFORE` trigger that calls `RAISE(ABORT, …)`.

## Indexes

- B-tree only. Partial indexes take a `WHERE` clause; expressions are indexed through a generated column or an expression index, deterministic functions only.
- `EXPLAIN QUERY PLAN` shows `SEARCH … USING INDEX` (good) or `SCAN` (full read).
- `PRAGMA optimize` after creating an index refreshes planner statistics.
- Billing counts rows read, not rows returned: `meta.rows_read` far above the returned row count marks a missing index.
- A batched `IN (…)` list is bounded by the bound-parameter limit: chunk the ids, or pass them as one JSON parameter read with `json_each(?)`.

## Search

- Full-text search is FTS5. An external-content table (`content='…'`) indexes the base table without copying it, kept in sync by insert, update and delete triggers.
- `lower()`, `upper()`, `LIKE` and `COLLATE NOCASE` fold ASCII only, so Turkish `İ`/`ı` (and any non-ASCII letter) mismatch. The application writes a locale-folded value into a separate column, and lookups, unique indexes and FTS use that column.
- `LIKE` and `GLOB` patterns have a small byte cap (see Limits).

## Access control

- There are no roles and no row-level security: any code holding the binding reads and writes everything.
- Tenant isolation lives in the data-access layer (every query takes a tenant id by construction), or in a database per tenant.
- Least privilege is per Worker: only Workers that need a database get its binding, and migrations run from a separate deploy identity.

## Limits (as of November 2026, verify)

| Limit | Workers Paid | Free |
|---|---|---|
| Database size | 10 GB, not raisable | 500 MB |
| Queries per Worker invocation | 1,000 | 50 |
| Time Travel window | 30 days | 7 days |

Same on both plans:

- SQL statement length: 100 KB.
- Bound parameters per query: 100.
- Query duration: 30 s, covering a whole `batch()`.
- String, BLOB or row size: 2 MB. Query result size: 50 MB.
- Columns per table: 100.
- `LIKE` / `GLOB` pattern: 50 bytes.
- Simultaneous connections per Worker invocation: 6.

## Location and replicas

- The primary is placed near the creating request unless a **location hint** is given at creation (`wrangler d1 create … --location=weur`). A hint is best effort.
- A **jurisdiction** (`eu`, `us`, `fedramp`) restricts where data runs and is stored. It is set at creation only and overrides the hint: data residency is decided before the database exists.
- Read replication is opt-in per database, and only queries made through the Sessions API use replicas. Writes always go to the primary; replicas lag.
- Read-your-writes: `withSession("first-primary")`, or carry `session.getBookmark()` to the next request and open `withSession(bookmark)`. `withSession()` alone accepts stale first reads.

## Migrations

- `wrangler d1 migrations create | list | apply`: numbered `.sql` files, applied in order, tracked in `d1_migrations`. There are no down migrations: forward-only. A failing migration is rolled back and the previous one stays applied.
- `ALTER TABLE` covers rename table, rename column, add column and drop column. Changing a type, a constraint, a default or a primary key is a **table rebuild**: create the new table, copy rows, drop the old, rename, recreate indexes, triggers and views.
- A rebuild of a referenced table starts with `PRAGMA defer_foreign_keys = on`. Deferral does not stop `ON DELETE CASCADE`: dropping the parent deletes child rows, so a rebuild is tested on a copy of the data first.
- A rebuild copies every row inside the query duration limit while other queries wait: large tables are rebuilt in chunks or avoided.
- Expand → contract still applies: old and new Worker versions run against the same database during a deploy.

## Backup and restore

- **Time Travel** is always on: restore to any minute inside the plan's window. A restore overwrites the database in place and cancels running queries; it returns a bookmark that undoes it. Cloning to a new database is not available.
- Retention beyond the window is a scheduled export to object storage.
- An export blocks other queries while it runs, and fails on a database with virtual tables: FTS5 tables are dropped before the export and recreated after.
- Restores are tested on a schedule by importing an export into a separate database.

## Testing

- Tests run against a real local D1 through the Workers Vitest integration (`@cloudflare/vitest-plugin`, formerly `@cloudflare/vitest-pool-workers`), which uses Miniflare.
- Migrations are read with `readD1Migrations()` in the Vitest config and applied with `applyD1Migrations()` in a setup file, so tests see the production schema.
- Storage is isolated per test file.
